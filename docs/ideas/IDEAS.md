# tcb 長期構想・追加機能要望

このファイルは、①②③(クラッシュ系バグ修正・macOS完全対応・Git運用)の
土台が完成した後に着手する長期的な設計構想と、実装を先送りにしている
追加機能要望をまとめたもの。日々の作業ログはCLAUDE.mdを参照。

## ④ 学習目的でのC++/Objective-C/Python/Perl5移植

2026-07-21、ユーザー判断で①完了を待たず前倒しし、C++移植に本格着手
(詳細はCLAUDE.mdの「これまでの作業」16番参照)。最終的には「オブジェクト
指向版tcb」のお手本をClaudeが示す、というゴールも希望されている。

- 2026-07-15時点の優先度: C++移植を最優先とする。Perl5については以前
  から検討していたが、実はperl4学習用に書いた試作ソースが手元にある
  とのことで、優先度はC++より下げてよいとのこと。加えて、Objective-C
  への移植が可能であれば、Perl5・Pythonより先に検討したいとの要望あり
  (優先順としては C++ → Objective-C → Perl5/Python のイメージ)。
- 動機の具体例: ARCモードの入れ子対応。今の一覧はアーカイブの中に
  さらにアーカイブファイルがあっても、それを選んで再度ARCモードに入る
  (どこまで潜っても同様に動く)ことができない。現状のCソースは場当たり
  的な作りで、この手の再帰的な機能追加が難しいとユーザーは感じている
  → オブジェクト指向設計への移行で、こうした拡張を楽に実装できるように
  したい、というのが動機のひとつ。

## 追加機能要望(C++移行後に検討、2026-07-15追記)

C++移植(④)後の実装検討事項として挙げられたもの。[]内は現状の挙動。

- 機能上必要な外部プログラムが無い場合、SHELLに切り替えて当該プログラムを
  自動インストール [ユーザーによる手動インストール]
- FGREP/EGREP: 検索後の画面でマッチした文字列をハイライト等で表示
  [文字装飾無し]
- tcb初回起動時、`~/.tcb`に`tcbrc`が無ければ`/usr/local/lib/tcb/tcbrc`を
  tcb自身がコピー [ユーザーによる事前コピーが必要]
- `^J^H`で表示するマニュアルを、ウィンドウサイズ変更に対応して都度成形
  [成形済みのためCOLUMN幅固定]
- `tcb.1`等「.数字」で終わるファイルを`.[0-9]`形式で指定できるよう
  EXEC設定を改善 [ベタ文字列でしか設定できない]
- 日本語manファイルへの対応 [`Tnippon`が使えなくなっていて未対応。
  そもそも日本語manの現状を作者自身が把握できていない]
- LOCATE:
  - `^Jl` → `updatedb`を実行 [現状はlocateの実行のみ]
  - `^J^L` → 前回の検索文字列を入力欄に残しておき、そのままEnterなら
    locateを再実行せず前回のlocate結果画面へ戻る。別の文字列を入力すれば
    通常通りlocateを実行 [現状は前回画面へ戻るだけ]
- 引数無しのtcb起動を多重に行おうとした場合、以下のようなメッセージで
  注意喚起した上で、続く二度目の起動(サスペンド中のケースを含む)では
  新プロセスが旧プロセスをkillしてから起動する
  [現状はユーザーが自分で現プロセスをkillする必要がある]
  ```
  tcb: Process-ID 8442 ...
       Already running.
  ```
- SIGSEGVからの回収機構(`menu.c`の`menu_clear()`、`setjmp`/`longjmp`で
  クラッシュを検知し状態を巻き戻して処理を継続する仕組み。ある程度
  操作を進めた状態でのクラッシュはこれで画面にエラーも出さず静かに
  回収・継続できている)が、「戻る先が無い」2パターン(pagerモードでの
  クラッシュ、または起動直後などディレクトリ一覧モードで前のモードが
  無い状態でのクラッシュ)の場合だけは、`tcb: Segmentation fault.`を
  出してプログラム自体を終了する設計になっている(`menu.c`の
  `is_pg() || (n.M == T_dir && *l.prev == K_z)`分岐)。この2パターンでも
  終了させず、可能な範囲で状態を巻き戻して継続できるようにしてほしい
  [現状はプログラム終了、それまでのhistoryが保存されない]
  (2026-07-18追記、KEYモードの`^J^H : HELP`行へのカーソル移動で
  セグフォする不具合<起動直後は再現がまさにこのパターンだった>の
  調査時に発見)
- `^Oa`(実行中の文字コード切り替えキー)を、押すたびに次の候補へ盲目的に
  切り替わる現状の2〜3値サイクルではなく、文字コード一覧を表示してその
  中から選択できるUIに改善する [現状はASCII→EUC→UTF-8→ASCII…の3値
  サイクルのみ(2026-07-20実装、CLAUDE.md参照)。画面が文字化けしている
  状態でも一覧のラベル(ASCII部分)から選んで対処できるようにしたい、
  という要望]。現行の場当たり的なC実装ではなく、C++移行後の洗練された
  クラス設計で対応してほしいとのことで、④より後回しでよい
  (2026-07-20、^Oaの3値化直後にユーザーから提案)。
- RM/MVでの権限拒否時、理由が分かるメッセージを表示する
  [現状は権限拒否がビープのみで理由が分からないことがある(get_col()の
  バイト単位パースが壊れていた件<2026-07-20修正、CLAUDE.md参照>で
  「一見権限の問題に見えるが実は違う」という混乱をユーザーが経験した
  ことがきっかけ)。バグというよりも予定の方がいいかもしれない、との
  ユーザー判断]
- tcb自身のPAGERモード(SHELLモードで`export PAGER='tcb -p <pid>'`と
  自動設定される、tcb自身をページャーとして使う仕組み)が、ANSIエスケー
  プシーケンス(色・属性)を解釈せず生のまま表示してしまう
  [現状は`less`のように色・属性を解釈した表示ができず、`git log`等の
  カラー出力コマンドをSHELLプロンプトから直接実行すると`^[[33m`等が
  そのまま表示される。`^Jp`(PROGRAM)経由で`less`を明示的に起動すれば
  正しく色付き表示されることを確認済みなので、tcb側の問題と判明。
  差し当たりの回避策は`git config --global core.pager less`や
  `PAGER=less <コマンド>`でlessを直接使うこと]
  (2026-07-20、`PAGER=... git log`の表示崩れをユーザーが発見)
- TAB補完の候補一覧表示挙動が、PROGRAM起動時(`^Jp`)とSHELLプロンプト
  直接入力時とで異なるように見える
  [`^Jp`経由で「ls -l ワールドニュース」[tab]→(共通プレフィックス
  まで補完)→[tab]→候補一覧が出て選択できる、という動作をするのに対し、
  同じSHELLプロンプトから直接同じ操作をすると2回目の[tab]で何も起きず、
  一度backspaceで1文字消してから[tab]するとようやく一覧が出る。
  両者とも内部的にはmake_list()(key.c)を共有しているようだが、
  呼び出し元(input_key() / input_shell())の状態管理に差があるらしく
  未調査。PROGRAMとSHELLの補完ルーチンが実質的に別実装なのであれば、
  まず単一の補完ルーチンに統合してから、その統合後のルーチンに対して
  この挙動差を改善するのが良いのではないか、とのユーザー提案]
  (2026-07-20発見、原因調査は未着手)
- GUI対応: 「猫の手スクロール」(ドラッグ量・速度に応じた慣性スクロール、
  ドラッグ中はマウスカーソルが矢印から猫の手の形に変わる)を実装したい。
  作者が過去に書いたGUIアプリ「cb」(console bufferの略)の機能をtcbへ
  移植するもの。1ドットスクロールごとに、画面下端の未表示領域へ次の
  行のグラフィックイメージを1/16ずつ描き足していき、1文字行分(=16ドット
  相当)スクロールし終えた時点で次行の画像が完成する、という当時の実装
  だったとのこと。
  - **本機能はメイン機能ではなく隠しモードとして提供する**(通常操作は
    従来通りキーボード主体のテキストUIのまま)。
  - ls一覧を含む、tcbの全てのテキスト表示画面がこの慣性スクロールへ
    移行できるようにしたい、との要望。
  - 移行時、現在使用中のフォント・背景色・文字色をそのまま引き継ぐ
    (見た目が変わらないまま操作方法だけグラフィカルになる、という
    シームレスな切り替えが必須)。
  - 実装環境としては、④のC++移行時に検討している「表示を抽象化した
    `Display`クラス」構想(termcap版`TerminalDisplay`とは別に、SDL2等を
    使うピクセル単位描画版`GraphicalDisplay`を後から追加実装として
    差し込める設計)であれば無理なく対応可能、とAssistant側で技術検証
    済み(SDL2の`SDL_CreateColorCursor()`でカーソル形状変更、部分矩形の
    テクスチャ/サーフェスブリットで「1/16ずつ」の描画手法を再現、
    ドラッグの速度計算で慣性を実現)。④着手時に`Display`をこの前提で
    設計しておくことで、GUI対応のための二度目の作り直しを避けたい。
  (2026-07-21、④C++移行の設計構想を相談する中でユーザーから提案。
  可能なら④の予定に組み込んでほしいとのこと)
