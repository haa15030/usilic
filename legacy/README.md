# legacy/ で行った作業のまとめ

このディレクトリは、2000 年の tcb 1.5b-1 を名前だけ usilic に変えて取り込んだもの(`b813bb4`)に、**クラッシュの修正だけ**を当てた旧版(usilic.old)です。
当時のソースをなるべくそのまま保つ方針なので、機能を足したり見た目を直したりはしていません。
ビルド・インストール・置き場所・Linux で SHELL モードを使うためのカーネルの作り方は `README.old.md` にあります。
ここでは、何をなぜ変えたかをまとめます(2026-10-21〜10-31)。

## ソースの中の印

当時と違う所には、すべて `usilic.old:` で始まるコメントを付けてあります。

```
grep -rn "usilic.old:" legacy/src legacy/config.sh legacy/Makefile legacy/usilicrc
```

で全部拾えます。
当時のコメントは英語だけ(ASCII)ですが、足したコメントは読みやすさを優先して日本語(UTF-8)で書いてあります(コンパイラはコメントの中身を読まないので、動きには関係ありません)。
取り込みからの差分(103 か所のかたまり)のどれにも印があることは、台本で確かめてあります。

## 言葉の説明

### UB(Undefined Behavior、未定義動作)

C 言語の規格が「この書き方をした時に何が起きるかは決めない」としている操作です。
コンパイラやライブラリは何をしてもよいことになっていて、たまたま思ったとおりに動くことも、データが壊れることも、落ちることも、止まることもあります。
同じソースでも、OS・コンパイラ・最適化の度合いによって結果が変わります。

20 年前の環境でたまたま動いていた UB が、今の環境で表に出たものが、今回の修正の多くを占めます。
legacy で見つかったものは次のとおりです。

- **重なった範囲の strcpy()**: `strcpy(buff, &buff[3])` のように、同じバッファの中で文字列を前へずらす書き方です。
  strcpy() は 2 つの領域が重ならないことを前提にしています。
  当時は先頭から 1 バイトずつ写す作りだったので正しく動いていましたが、今は次のことが起きていました。
  - macOS: 重なりを検出して止まる(SHELL モードのフリーズ)。
  - Linux(aarch64): 速く写すために順番を変えるので文字が化ける(usilicrc の「K-11」が「K11」に、「previous」が「reviouss」に)。

  重なっていても正しく写すと決められている `memmove()` に置き換えました(28 か所)。
- **sprintf(tmp, "%s/s.", tmp)**: 書き込み先と読み出し元が同じバッファです。
  実際に tmp が「/s.」だけに壊れ、作業用のファイルを開けずに落ちていました。
- **fileno(NULL)**: fopen() の失敗を確かめずに使っていました。
- **関数の型を偽った呼び出し**: 引数 2 つの関数を、引数の無い関数の型に無理に変えて呼んでいました(KEY モードの segv)。

### 64bit でのポインタの切り詰め

当時の 32bit の環境では、ポインタ(メモリの番地)と `int`・`u_int` が同じ 4 バイトだったので、ポインタを整数の変数に入れても失われませんでした。
今の 64bit の環境ではポインタが 8 バイトなので、4 バイトの整数に入れると上の半分が捨てられ、取り出した番地は別の場所を指します。
legacy では、ARCHIVE の設定の配列・アーカイブの中の位置(`PP.tell`)・`FILE*` を整数で受け渡ししていて、ARC モード等で落ちていました。
ポインタを入れても失われない `uintptr_t` に替えました。

切り詰めとは少し違いますが、同じ「32bit ではポインタが 4 バイト」という前提で、番地の差を 4 で割って配列の何番目かを出していた所もあります(`load_ll()`)。
64bit では 1 つの欄が 8 バイトなので番号が 2 倍になり、(ls) やファイルのカーソルの位置を違う欄へ保存しようとして捨てていました(戻ると最上行になる)。

似たものに、配列の終わりの印 `-1` で配列の外を読んでいた所があります(`is_child()`)。
32bit の頃はそこにたまたま有効なポインタがあり、64bit では NULL になって落ちていました。

### バッファの溢れ

決まった大きさの文字の配列に、それより長い文字列を入れていた所です。
版の表示の文字列(83 バイト)を `version[80]`・`usilic[10]` に入れていて、名前が tcb から usilic.old に長くなったことで、必ず溢れるようになっていました。

## 当てた修正

| 何が起きていたか | 原因 | 主な場所 |
|---|---|---|
| 起動時の segv | ARCHIVE の配列のポインタの切り詰め、コメントアウトされていた `conf_arc()` | str.c |
| SHELL が無い時の segv | `getenv("SHELL")` の NULL を strcpy() | str.c |
| ARC モードの segv | アーカイブの中の位置・`FILE*` を `u_int` に入れていた | usilic.h・alloc.c・fork.c |
| macOS の tar の一覧で止まる | BSD tar の一覧の形(所有者とグループの間に `/` が無い)で、逆向きの走査が終わらない | alloc.c |
| 日本語の日付でアーカイブの一覧が壊れる | 一覧を読む子のロケールが日本語のまま | fork.c(`LC_ALL=C`) |
| 起動時のハング・文字化け | 重なった strcpy()(UB) | 全ソース |
| SHELL モードのフリーズ・クラッシュ | バッファの溢れ、重なった strcpy()、sprintf() の自己参照 | shell.c・usilic.c |
| SHELL モードの改行の無限ループ | GNOME Terminal 等の `PROMPT_COMMAND` が出す制御文字を、プロンプトの一部として読んでいた | shell.c |
| KEY モードの segv | 関数の型を偽った呼び出し(UB) | key.c |
| 二重に動く usilic | `execvp()` に失敗した子が終わらずに親の続きを走る | fork.c |
| 開いた fd を壊す | `pipe()` の呼び忘れ | str.c |
| macOS で SHELL のキーで固まる | 開けない古い擬似端末を、待つ形で開いていた | sub.c(`O_NONBLOCK`) |
| bzip2・nkf 等に通すファイルで segv | `is_child()` が配列の外を strcmp() | child.c |
| (ls)・ファイルの位置が保存されず最上行に戻る | `load_ll()` が欄の番号を 4 バイトで割って出していた(64bit で 2 倍にずれる) | mode.c |
| 行が描かれないことがある(まれ) | ポインタを `int` に入れて NULL かを見ていた | disp.c |

修正のほとんどは、`old/` の方で先に見つけて直したもののうち、クラッシュに関わるものだけを持ってきました(各コミットのメッセージに元のコミットを書いてあります)。

## ビルドまわり

- **macOS でビルドできるように**: config.sh に Darwin の分岐を足し、`sys/types.h` を読むようにし(u_char 等)、sigaction の初期化を glibc に頼らない書き方にしました。
- **新(C++ 版)と並べて入れる**: 名前・置き場所・環境変数を usilic.old にしました(`~/.local/bin/usilic.old`・`~/.usilic.old/`・`USILIC_OLD` 等)。
  環境変数が新と同じ `USILIC` だと、互いの SHELL の中で起動した時に相手を自分の親と取り違えます。
- **バイナリの名前**: make で作るものも `src/usilic.old` にしました(C++ 版の usilic と紛らわしいため)。
- **.PHONY**: 以前は legacy/ で make しても、`src/config.h` より新しいバイナリがあると src/ へ降りず、.c を直しても作り直されませんでした。
  `.PHONY` を付けて毎回 src/ の make へ降りるようにしました(作り直すのは直した .c の分だけです)。

## キーの割り当て(設定だけ、ソースは変えていない)

usilicrc の KEY 節で、C++ 版の usilic と同じ機能のキーは、C++ 版のキーに合わせました(2026-10-31)。
行の順番で機能の番号(K-n)が決まるので、行の並びは当時のままで、キーとコメントだけを書き換えています。
コメントは日本語(EUC)です。

- 接頭キー F-2 は ^X^K から ^J^O に(ERROR は ^J^Oe、SHELL のログは ^J^Os)。
- CP・MV・RM・ARC は ^Oc・^Om・^Or・^Oa、全選択・全解除は ^Oy・^On。
- カレントディレクトリへ ^J^C、親ディレクトリへ ^J^B、ls の表示形式 ^Oo、SHELL の再起動 ^Js、EDIT ^[e。
- CUT(バッファ)は ^Jp・^J^P(C++ 版の PART)、PROGRAM は ^Jt・^J^T(C++ 版の TOOL)。
- マクロの「選択して上へ・下へ」は [ ・ ](元は , ・ .)。
- C++ 版に無い機能は、C++ 版で空いているキーに置きました: ascii モード ^O^A、表示の漢字コード ^O^K、file の CUT の一覧 ^JB。
- USILIC(K-0)だけは ^T のままです(C++ 版は ^[u ですが、この行では ESC で始まるキーが効きません)。
- `doc/HELP.jp` 等の文書は当時のキーのままです。

## UTF-8 のファイルを読む(設定だけ、ソースは変えていない)

legacy は EUC を前提にしているので、UTF-8 のファイルを開くと化けます。
ソースには手を入れず、usilicrc の FILE 節(拡張子ごとに中身を通すプログラム、`.gz` を `gzip -dc` に通すのと同じ仕組み)で、よく使う拡張子を `nkf -e` に通して EUC にしてから読むようにしました。

```
FILE
	.gz	gzip	-dc
	...
	.txt	nkf	-e
	.md	nkf	-e
	...
```

- 対象は `.txt .md .rst .org .tex .notes .c .h .cpp .hpp .mm .py .php .js .ts .sh .pl .json .yml .yaml .toml .ini .conf .csv .tsv .xml .opf .xhtml .css .log .1 .man .jp` です。
- nkf は入力の文字コードを判別するので、もともと EUC のファイルもそのまま通ります。
- `.html`・`.htm` は EXEC 節で lynx に渡しているので入れていません。
- 拡張子の無いファイル(README・HELP 等)と、ファイル名そのものには効きません。
- インストール済みの `~/.local/lib/usilic.old/usilic.oldrc` は、`make install` のたびにこのディレクトリの `usilicrc` で上書きされます。

## 表示を EUC にする(端末の設定)

legacy の画面の日本語は EUC で出るので、端末の文字コードを EUC にすると読めます。
EUC の窓では legacy 以外の UTF-8 の出力(ファイル名等)が化けるので、EUC 用のプロファイルを別に作り、legacy の時だけそれを使うのが便利です。

- **macOS の Terminal.app**: 「設定」→「プロファイル」→「詳細」→「テキストエンコーディング」で「日本語 (EUC)」。
- **Ubuntu の GNOME Terminal**: プロファイルの「互換性」→「エンコーディング」で「日本語 (EUC-JP)」。
  Ptyxis(最近の Ubuntu の標準の端末)には、文字コードを選ぶ設定が見当たりません。
- **端末を選ばない方法**: `luit -encoding EUC-JP usilic.old` で、UTF-8 の端末のまま legacy の入出力を変換させます(Ubuntu では `sudo apt install luit`)。
